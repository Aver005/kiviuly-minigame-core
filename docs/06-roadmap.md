# 06 — Дорожная карта

Порядок работ по возрастанию риска. Каждая фаза оставляет систему в рабочем
состоянии: игры не должны «лежать» между фазами. Single-server работает уже после
фазы 1; сеть подключается на 2–3.

## Обзор

> **Фактический порядок отличается от исходного (решение владельца):** сначала
> ПОЛНОСТЬЮ объединить все три игры на ядре (включая Escape), и лишь потом — сеть.
> Поэтому «фаза 4» (Escape) сделана раньше «фаз 2–3» (MySQL/хаб). Статус ниже.

| Фаза | Итог | Статус |
|---|---|---|
| 0 | `mg-api` + `mg-core` (вынутое ядро), сборка есть | ✅ готово |
| 1 | skywars и sbw переведены на `depend: [MgCore]` | ✅ готово |
| 4 | `escape` мигрирован под шов `Minigame` | ✅ готово (см. `07`) |
| — | сквозная статистика (generic-счётчики, SQLite) + оффлайн-rejoin | ✅ готово сверх плана |
| 2 | `StatsService` → **MySQL**: статистика сквозная по сети | ⏳ после объединения |
| 3 | `mg-hub`: селектор + профиль + транспорт | ⏳ после объединения |
| 5 | `Team`, лидерборды-UI, лобби-PvP, очередь, `mg-proxy` | ⏳ по надобности |

> Единый прогон трёх игр на одном сервере (сквозной тест) — не проводился ни разу;
> запланирован в самом конце (решение владельца), правки копятся одним пакетом.

---

## Фаза 0 — вынести ядро

**Цель:** отдельный собираемый мультимодуль с `mg-api` и `mg-core`.

Шаги:
1. Завести Gradle-мультимодуль (`settings.gradle.kts` c `mg-api`, `mg-core`),
   toolchain Java 25, Paper 26.1.2 — как в текущих играх.
2. Взять ядро из **`skyblockwars-reborn`** (самый свежий, богатейший набор хуков
   `Minigame`) как основу. Не из skywars — свести drift потом.
3. Разложить на два модуля:
   - `mg-api` ← интерфейсы: `GamePhase`, `Arena`, `Match`, `MatchPlayer`,
     `MatchResult`, `Minigame`, `MinigameDescriptor`, `DataKey`, `StatsService`,
     `MgCore`, `TransportService`/`QueueService` (пока заглушки).
   - `mg-core` ← реализация: `GameSession` (реализует `Match`), `ArenaManager`,
     `PlayerSnapshot`, `menu/*`, `ui/*` (HUD), `listener/*`, `util/*`
     (`Msg`/`Keys`/`Items`/`DebugLog`), `StatsService` (SQLite-бэкенд).
4. Переименовать пакет `ru.kiviuly.skyblockwars` → `ru.kiviuly.mg`, команду `sbw` →
   `mg` (админ-команда ядра).
5. Разнести «статические синглтоны» (`Msg`/`Keys`/`DebugLog`) за фасад `MgCore`
   (или оставить static, но инициализировать один раз в `mg-core`, раз владелец один).
6. `mg-core` регистрирует `MgCore` в `ServicesManager` на `onEnable`.

**Готово, когда:** `mg-core` собирается и запускается как самостоятельный плагин
(с dummy `TemplateGame`), заводит арену, гоняет пустой матч.

---

## Фаза 1 — перевести skywars и sbw на core

**Цель:** две «wars» больше не содержат копии ядра — только правила.

Шаги (для каждой игры):
1. Удалить из репо игры пакеты `arena/`, `game/` (кроме своего `*Game`),
   `player/`, `stats/`, `ui/`, `menu/` (кроме своих меню), `listener/` (кроме своего),
   `util/`.
2. Заменить зависимость на `compileOnly(project(":mg-api"))` + `depend: [MgCore]`.
3. Переписать `*Game extends Minigame` под новый контракт (`Match` вместо
   `GameSession`, `descriptor()` вместо `id()/displayName()`, `DataKey` вместо
   строковых настроек). Логика правил не меняется — только типы.
4. Свести drift: то, что в skywars и sbw ядро делало по-разному, теперь одно в core.
5. Прогнать оба на тестовом сервере: вход, отсчёт, матч, выбывание, итоги, откат.

**Готово, когда:** обе игры работают как раньше, но их репозитории тонкие. Это
момент, когда дублирование кода реально устранено (главная боль из
[00-vision.md](00-vision.md)).

**Риск/чек:** поведение отсчёта, HUD, снапшотов должно совпасть 1:1 со старым.
Держать под рукой старые jar для сравнения.

---

## Фаза 2 — общая MySQL

**Цель:** статистика сквозная, даже до появления хаба.

Шаги:
1. Реализовать `MySqlStatsBackend` (контракт `StatsService`, схема из
   [05-storage-and-stats.md](05-storage-and-stats.md)).
2. Шейдить драйвер+пул в `mg-core` (не в игры).
3. `storage.yml`: `backend: mysql` + креды. SQLite оставить дефолтом для dev.
4. `MinigameDescriptor` публикуется в таблицу `games` при `register`.
5. Проверить: два сервера с разными играми пишут в одну БД; профиль по обоим.

**Готово, когда:** статистика с двух игровых серверов сходится в одном профиле.

---

## Фаза 3 — хаб

**Цель:** единый вход, выбор игры, сквозной профиль.

Шаги:
1. `mg-hub` (Paper-плагин на хабе, зависит от `mg-api`).
2. Селектор игр: читает `games` + `MinigameDescriptor`, GUI/компас.
3. `TransportService` через plugin-messaging (Velocity `Connect`).
4. Профиль/лидерборд на хабе: `StatsService.profile` / `top`.
5. Настроить Velocity, зарегистрировать backend-серверы.

**Готово, когда:** игрок с хаба выбирает игру и попадает в матч на нужном сервере.

---

## Фаза 4 — мигрировать escape

Самый трудный кусок — отдельный документ [07-escape-migration.md](07-escape-migration.md).
Коротко: распилить монолит `GameSession` (2149 строк), правила вынести в
`EscapeGame extends Minigame`, инфраструктуру заменить на общую из `mg-core`.

**Готово, когда:** escape работает поверх core, богатые механики (контракты,
торговцы, модификаторы, темы, respawn-блоки) сохранены.

---

## Фаза 5 — платформенные фичи

По мере надобности, независимо:
- `Team` довести до реального командного режима (2v2 и т.п.).
- Лидерборды-UI на хабе (топы по играм/статам).
- Лобби-PvP / дуэли на хабе (как `Minigame` поверх `mg-core`).
- `mg-proxy` (Velocity): авторитетная очередь, presence, выбор сервера по нагрузке.
- Redis для presence/party/кросс-хаб-очереди, если серверов станет много.

---

## Принципы миграции

- **Ни одна фаза не ломает работающие игры.** Между фазами всё запускается.
- **Сначала самое дешёвое и ценное** (устранение дублирования), потом сеть, потом
  монолит.
- **Старые jar под рукой** для сравнения поведения после фаз 1 и 4.
- **Тестовый сервер** через `deploy`-таск (как в текущих играх).
