# 04 — Сеть: хаб, прокси, транспорт

Как устроена сетевая часть. На single-server всё ниже вырождается в no-op —
`mg-core` работает и без сети (см. фазу 1 в [06-roadmap.md](06-roadmap.md)). Этот
слой подключается на фазах 2–3.

## Целевая топология

```
            ┌─────────────┐
            │   Velocity  │  прокси — единая точка входа игроков
            │  (mg-proxy) │
            └──────┬──────┘
      ┌────────────┼────────────┬───────────────┐
   ┌──▼───┐   ┌────▼────┐  ┌────▼─────┐   ┌──────▼──────┐
   │ HUB  │   │ skywars │  │ sbw      │   │ escape      │
   │mg-hub│   │ +mg-core│  │ +mg-core │   │ +mg-core    │
   └──────┘   └─────────┘  └──────────┘   └─────────────┘
        │           │            │               │
        └───────────┴────────────┴───────────────┘
                          │
                   ┌──────▼──────┐
                   │  MySQL/     │  сквозная статистика + профиль
                   │  MariaDB    │  (+ Redis позже)
                   └─────────────┘
```

- **Игрок** всегда заходит через прокси. Прокси кладёт его на **хаб**.
- **Хаб** (`mg-hub`) — выбор игры, сквозной профиль, PvP/дуэли в лобби. Отправляет
  игрока на нужный игровой сервер.
- **Игровой сервер** (`mg-core` + игра) — арены, лобби арен, матчи. По окончании
  может вернуть игрока на хаб (`transport().sendToGame(p, "hub")` или аналог).
- **MySQL** — общая для всех: статистика и профиль читаются/пишутся из любого узла.

## Что делает хаб (`mg-hub`)

Отдельный плагин, только на хаб-сервере. Зависит от `mg-api`; **не** содержит кода игр.

- **Селектор игр.** Читает список зарегистрированных `MinigameDescriptor` из общей БД
  (их туда публикует каждый `mg-core` при `register`). Рисует GUI/компас с карточками
  (иконка, имя, онлайн, в очереди). Клик → `QueueService.enqueue(p, gameId)` или сразу
  `TransportService.sendToGame(p, gameId)`.
- **Сквозной профиль.** По входу тянет `StatsService.profile(uuid)` — статистика по
  всем играм в одном месте. Сайдбар/меню профиля, лидерборды (`top(...)`).
- **Лобби-PvP / дуэли** (фаза 5). Отдельный игровой режим на хабе; можно реализовать
  как обычную `Minigame` поверх `mg-core`, поднятого и на хабе, — тогда «сражения в
  лобби» бесплатно переиспользуют движок матчей.

## Транспорт игроков (`TransportService`)

Отправка игрока между серверами сети. Два варианта реализации:

1. **Plugin-messaging (проще, без своего прокси-плагина).** Backend шлёт
   `BungeeCord`-канал сообщение `Connect <server>`. Velocity поддерживает этот канал
   при `bungee-plugin-message-channel` / соответствующей опции. Минус: только
   «отправить», без обратной связи и без авторитетной очереди.
2. **Свой Velocity-плагин `mg-proxy` (надёжнее, рекомендуется для сети).** Backend
   общается с прокси по собственному messaging-каналу. Прокси — авторитет: держит
   presence (кто где), считает очередь, выбирает наименее загруженный сервер игры,
   переносит игрока. Здесь же живёт `QueueService`-логика.

На single-server `TransportService` — no-op (некуда отправлять), `sendToGame(p,"hub")`
просто игнорируется. Игры этого не замечают — они всегда зовут один интерфейс.

## Очередь / матчмейкинг (`QueueService`)

- **Простой режим (фаза 3).** Хаб держит очередь на `gameId` в памяти; когда набрано
  ≥ `minPlayers`, отправляет пачку на игровой сервер, где `mg-core` заводит их в арену.
- **Сетевой режим (фаза 5).** Авторитет очереди — `mg-proxy` (или Redis-структуры),
  чтобы очередь была общей для нескольких хабов/инстансов. Выбор сервера — по
  свободным аренам и нагрузке.

## Общая БД (MySQL/MariaDB)

Единственный способ сделать статистику и профиль сквозными в сети — общее хранилище,
к которому обращаются все узлы. Подробности схемы и бэкендов —
[05-storage-and-stats.md](05-storage-and-stats.md). Ключевое:

- Все `mg-core` и `mg-hub` указывают на одну MySQL (креды в `storage.yml`).
- `MinigameDescriptor` каждой игры публикуется в таблицу `games` при `register` →
  хаб знает про игру, не имея её кода.
- Presence (кто где) — на старте можно и в MySQL; при росте вынести в Redis.

## Порядок включения сети

Транспорт/очередь/хаб проектируются как заглушки-интерфейсы с самого начала, но
включаются постепенно:

1. Фаза 2 — общая MySQL: статистика уже сквозная, даже без хаба.
2. Фаза 3 — `mg-hub` + транспорт (plugin-messaging): рабочий выбор игры и переход.
3. Фаза 5 — `mg-proxy` + авторитетная очередь + лобби-PvP.

Открытые вопросы по сети (транспорт Velocity vs Bungee, presence в MySQL vs Redis,
где живёт очередь) — в [08-decisions.md](08-decisions.md).
