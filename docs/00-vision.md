# 00 — Зачем это всё

## Проблема

Есть три мини-игры под Minecraft (Paper), у которых огромное пересечение по коду и
понятиям:

- `escape-reborn` — «Escape», тюремный last-man-standing.
- `skyblockwars-reborn` — SkyBlockWars.
- `skywars-reborn` — SkyWars.

Во всех трёх повторяется одно и то же: арены, лобби с отсчётом, матч с фазами и
таймером, выбывание/спектейт, снапшот игрока до матча и восстановление после,
откат изменённого мира, статистика, HUD (сайдбар/босс-бар), меню, i18n. Сейчас это
живёт тремя копиями, которые расходятся.

## Что показал разбор трёх проектов

Это **не три равных случая, а два поколения одного дизайна**:

| | escape-reborn | skywars-reborn | skyblockwars-reborn |
|---|---|---|---|
| groupId | `me.aver005.escape` | `ru.kiviuly.skywars` | `ru.kiviuly.skyblockwars` |
| Ядро | монолит `GameSession` **2149 строк**, без шва расширения | game-agnostic core + `Minigame` | game-agnostic core + `Minigame` |
| Стиль | service-locator через `EscapePlugin`, много механик (контракты, торговцы, модификаторы, темы, respawn-блоки, `GameEvent`) | «mcmgp-template»: правила изолированы в `SkyWarsGame` | «mcmgp-template»: правила изолированы в `SkyBlockWarsGame` |
| Стек | Paper 26.1.2, Java 25, Gradle KTS, 0 внешних зависимостей | идентично | идентично |

**Ключевой вывод.** `skywars-reborn` и `skyblockwars-reborn` уже собраны из одного
game-agnostic ядра с единственным швом расширения — абстрактным `Minigame`. Их
пакеты `arena/`, `game/`, `player/`, `stats/`, `ui/`, `menu/`, `listener/`, `util/`
почти байт-в-байт совпадают и потихоньку расходятся (drift). То есть абстракции
**Арена / Матч (`GameSession`) / Игрок-в-матче (`MatchPlayer`) / Результат
(`MatchResult`) / Фаза (`GamePhase`) уже спроектированы и работают** — просто
скопированы в два репозитория.

`escape-reborn` — старшее поколение: богаче механиками, но это один класс на 2149
строк без шва `Minigame`.

Поэтому задача — **не проектировать API с нуля**, а поднять уже существующее ядро в
отдельный модуль `mg-core`, устранить дублирование, и подтянуть монолит `escape`
под тот же шов. Это сильно снижает риск.

## Две разные вещи, которые надо развести

В идее «общий API» спрятаны два разных продукта:

1. **Фреймворк / библиотека (compile-time).** Общие абстракции Арена/Матч/Игрок,
   которые каждая игра реализует по-своему. Это то, что уже есть в двух «wars».
   Решает **дублирование кода**.
2. **Runtime-платформа (хаб).** Общий лобби-сервер с выбором игры, сквозная
   статистика между играми, PvP/дуэли в лобби, очередь. Это **живой сервис**, к
   которому игровые серверы подключаются в рантайме. Решает **«единый профиль и
   лобби на всю сеть»**.

Нужно и то, и другое — они складываются в одну систему, но реализуются разными
модулями (`mg-core` vs `mg-hub`/`mg-proxy`).

## Топология (принятое решение)

Сейчас сервер один, но целевая схема — **сеть за прокси**:

```
            ┌─────────────┐
            │   PROXY     │  Velocity  ← маршрутизация игроков между серверами
            │  (mg-proxy) │
            └──────┬──────┘
      ┌────────────┼────────────┬───────────────┐
   ┌──▼───┐   ┌────▼────┐  ┌────▼─────┐   ┌──────▼──────┐
   │ HUB  │   │ skywars │  │ sbw      │   │ escape      │
   │mg-hub│   │ +mg-core│  │ +mg-core │   │ +mg-core    │
   └──────┘   └─────────┘  └──────────┘   └─────────────┘
        │           │            │               │
        └───────────┴────────────┴───────────────┘
                          │
                   ┌──────▼──────┐
                   │  MySQL/     │  сквозная статистика + профиль
                   │  MariaDB    │  (+ Redis позже: presence/queue/party)
                   └─────────────┘
```

- **Хаб** — отдельный сервер: селектор игр, показ сквозного профиля, PvP/дуэли,
  отправка игрока на нужный игровой сервер.
- **Игровой сервер** — `mg-core` (движок) + тонкий плагин-игра. Лобби арен — здесь.
- **Сквозная статистика** — не локальный SQLite у каждого плагина, а **общая
  MySQL**, куда пишут все серверы. Это единственный способ сделать статистику
  общей в сети.

Два следствия, которых нет в текущих репах и которые надо заложить в абстракции
сразу:

1. **Хранилище статистики абстрагируется** (`StatsService`): SQLite-бэкенд для
   одиночного/dev-сервера работает сегодня, MySQL-бэкенд включается для сети без
   переписывания игр.
2. **Появляется межсерверный транспорт** (`TransportService`): отправка игрока
   хаб→игровой сервер через прокси.

## Цели

- Один core-модуль вместо трёх копий; игры — тонкие.
- Новая игра пишется в одном классе-наследнике `Minigame`, без копипасты инфраструктуры.
- Single-server работает сразу; сеть подключается позже без переписывания игр.
- Сквозной профиль и статистика на всю сеть.
- Не сломать три уже работающие игры в процессе.

## Не-цели (пока)

- Переписывать игровую логику `escape` (только вынести инфраструктуру под шов).
- Redis/шардинг на старте — MySQL закрывает статистику и профиль.
- Античит, экономика, кастомные world-gen — вне рамок core.
