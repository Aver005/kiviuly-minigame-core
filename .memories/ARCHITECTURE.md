# ARCHITECTURE
> Layers, the core loop/model, data flows, and the *why* behind big decisions.
> Last updated: 2026-07-24

## Слои

```
mg-api   — контракты + общий тулкит. От него зависят игры (compileOnly) и ядро.
mg-core  — Paper-плагин: движок матча, реестр арен/игр, команды, меню, статистика.
игры     — тонкие Paper-плагины: depend: [MgCore], реализуют Minigame.
```

Зависимости строго в одну сторону: всё смотрит на `mg-api`, `mg-api` — ни на кого.

## Несущая модель

- **`Arena`** — статический конфиг площадки: мир, лобби, спавны, лимиты, тайминги.
  Игро-специфика лежит в двух универсальных «карманах»: числа (`getSetting`) и
  именованные группы точек с ярлыками (`spots(group)`). Благодаря этому новая игра
  не требует правок контракта арены.
- **`Match`** — контракт одного матча, который видит игра. Реализация — `GameSession`
  в ядре. Управляющие методы движка (`addPlayer`, `forceStart`, `forceCleanup`) в
  контракт НЕ входят: их зовёт только ядро.
- **`Minigame`** — точка расширения. Логика без состояния: одна инстанция на плагин,
  состояние матча — в самом матче. Ядро ведёт матч, `Minigame` решает, что он значит.

## Жизненный цикл матча (ведёт ядро)

`LOBBY → COUNTDOWN → RUNNING → ENDING`, один тикер 1 Гц. На переходах ядро зовёт
хуки игры: `onLobbyJoin` → `giveLoadout` (каждому) → `onStart` → `onTick` (раз в
секунду) → `onLethalDamage`/`onPlayerEliminated` → `checkResult` (не-null завершает)
→ `onEnd` → откат мира и снапшотов → `onCleanup`.

## Как игра находит ядро (SPI)

Ядро публикует фасад `MgCore` в Bukkit `ServicesManager`; игра забирает его в
`onEnable` и регистрирует себя. Игра компилируется только против `mg-api` —
реализацию ядра она не видит. `depend: [MgCore]` в `plugin.yml` гарантирует порядок
загрузки.

**Почему так, а не shaded-библиотека:** нужен один владелец общего состояния
(статический каталог сообщений, PDC-ключи, реестр арен, статистика). При shading у
каждой игры была бы своя копия статиков — они бы конфликтовали.

## Мульти-игровая модель

Ядро держит **реестр игр** (`Map<id, Minigame>`), а не одну игру. Из этого следует:

- **Арена принадлежит игре** (`Arena.getGameId()`), поэтому id арены уникален только
  внутри игры. Разрешение неоднозначности — в `MinigameCommand.resolveArena`.
- **Арены хранятся в папке своей игры** (`Minigame.dataFolder()` → `arenas/<ID>.yml`),
  а не у ядра. Решение владельца: «каждая мини-игра владеет своими данными».
  Исключение — платформенные данные (снапшоты игроков, `stats.db`) у ядра, потому что
  статистика задумана сквозной по всем играм.
- **Команда привязана к игре**: `core.commandFor(game)` отдаёт обработчик, который
  видит только её арены и делегирует незнакомые подкоманды только ей. Платформенная
  `/mg` работает поверх всех арен и принимает slug игры при конфликте id.
- **Права**: общее `mg.admin` покрывает всё; у каждой игры своё короткое
  (`Minigame.adminPermission()`, напр. `sw.admin`). Связка сделана кодом (`mg.admin ||
  право игры`), а не через `children` в `plugin.yml` — ядро на момент сборки не знает
  списка игр.

## Инварианты платформы

1. **Откат мира**: перед изменением блока — `match.rememberBlock/rememberState`,
   на заспавненную сущность — `match.trackEntity`. Не запомнил — не откатится.
2. **Целость игрока**: вход в матч = снапшот + очистка; любой выход = восстановление.
   Файл снапшота на диске — страховка от краша.
3. **Тексты** только из `messages.yml` через `Msg`; ни одной строки игроку в Java.
4. **Данные предметов** только через PDC (`Keys`), никогда не парсить имена/лор.
5. **Вся игровая логика — main thread**; async только у хранилища статистики.

## Что пока не сделано осознанно

- `MatchResult` до сих пор на `List<UUID>`, не на `Team` — перевод отложен до реального
  командного режима (ломающий рефактор движка).
- `Team` отдаётся движком как FFA-заглушка (по команде на игрока).
- `StatsService.top(gameId, …)` игнорирует `gameId` — хранилище пока одно-игровое.
- `TransportService`/`QueueService` — контракты заложены, реализации нет
  (`LocalTransport` = no-op), потому что сеть идёт после объединения игр.
